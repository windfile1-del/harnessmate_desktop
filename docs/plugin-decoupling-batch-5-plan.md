## 4. 最小内核边界与平级原则

| 留在内核的机制 | 必须由普通插件拥有的产品功能 |
| --- | --- |
| 进程启动/退出、单实例、基本窗口、日志和必要诊断 | 默认应用布局、主题方案、侧栏、Inspector、命令面板、通知策略、菜单和托盘业务动作 |
| 包发现/安装/修订、首次来源信任、实例/依赖/绑定、组合提交与回退、可撤销生命周期 | 设置、插件中心、来源浏览、组合编辑器、AI 插件开发工具及其交互 |
| 服务目录、事件/调用、HTTP/WS/IPC 通用传输、身份校验及已有本地管理边界 | 业务 API、旧业务 URL/WS 协议适配、配对/设备管理、远程同步 |
| 文件、进程、网络、数据库连接/事务、桌面视图等通用资源原语 | 会话、驱动、AGY、审批策略、Git、终端、历史、搜索、账本等领域读写/任务/投影 |
| 最小恢复视图和独立恢复 API，通用迁移记录 | 各领域建表/迁移/查询，产品欢迎页及管理整页 |

内核不是默认业务的集合。通用能力须同时能被预装和外部插件使用，不能用“内部服务”“内置 ID”保留不可替换的业务入口。最小恢复视图只处理诊断、停用坏实例、导入/选择组合、安装已信任来源或完成现有信任流程、恢复修订和重启，不承载完整插件市场或 AI Builder。

允许同类实现、多实例和不同组合同时存在；单个窗口当前应用入口由显式绑定选择，是挂载位置的选择，不是插件等级。布局可定义自己的区域，业务插件通过贡献和服务接入，不要求所有布局采用相同三栏或会话模型。

可信插件继续使用已授权的代码及 OS 能力，不新增官方签名门槛、厂商保留类别、逐业务弹窗或人为实例上限。保留既有来源信任、真实身份和运行代次验证；模型工具审批与可信插件执行权限分别处理。前端使用公开可信模块/桥接或已支持的隔离模式，不为获取自由度而把 Node 无条件注入所有页面。

## 5. 统一公共接缝与资源规则

下面的接口名是**本批拟定语义，不表示候选中已存在同名 API**。W1 先盘点既有服务、视图、路由、命令与导航机制，优先扩展已有通用接口；确有缺口才增加最小原语，并同步契约和示例。

| 接缝 | 最少语义 | 交付者/消费者 |
| --- | --- | --- |
| 应用入口能力（如 `application.view.v1`） | 由组合选择 instanceId 和视图入口；挂载/卸载/代次；错误进入恢复；不能硬编码默认布局组件 | W1 提供，W2/W3 消费 |
| 导航请求 | 目标 instanceId/pageId、领域 context、placement、requestId；返回 accepted/unavailable/failed；布局解释位置，内核不理解 session/file 等业务 | W1 提供；文件/会话 DTO 由已有领域契约拥有 |
| UI 贡献 | 页面、区域、命令、菜单/托盘动作、设置页的注册/查询/订阅与 disposer；贡献目标和上下文由插件定义 | W1 基础、W2 管理接线；无需增加每种业务一个内核 action |
| 配置编辑 | 声明 schema/版本或自定义设置视图，实例明确；验证和保存结果由所有者返回 | W2 提供，所有领域消费 |
| 安装开发工作流 | 调用现有安装、修订、启停、绑定、恢复 API；构建/生成任务支持诊断、取消和重连 | W2 开发工具，不将流程编排搬入内核 |
| 持久化/迁移 | 复用现有通用存储或连接；必要时补连接/事务/命名迁移原语；迁移按所有者和版本幂等执行 | W1/W2 清单，W3 收尾 |
| 远程接入 | 可撤销认证提供者、连接资源、路由注册、订阅与有界批次/游标 | W3；内核不枚举远程业务帧 |

当前公开 `context.storage` 是插件/工作区 KV，不能假定已经提供 SQL API。可信插件可使用已有宿主资源或自身数据库，领域数据提供者不得被迫使用默认 SQLite。为兼容默认库而新增的连接/迁移原语也必须公开可用，不能暴露私有 HarnessMateStore 作为 SDK。

所有回调、页面、快捷键、菜单、定时器、订阅、路由、认证注册和数据库句柄标明 instanceId 与运行代次，停用时注销；迟到回调不能作用于新实例。共享底层 WS 可以复用，业务订阅须能逐实例撤销，不让每个页面建立一套全局 socket/store。

## 6. B5-W1：应用布局、导航与前端状态归属

分支：`codex/b5-w1-shell`。交付完整后 W2 才正式开发。

### 6.1 实施步骤

1. 建立入口、组件、store 字段、快捷键、菜单动作与订阅的所有权清单；逐项写出保留/迁出位置。先提交可运行的公开应用入口/导航/贡献契约、测试夹具和一份外部最小布局，不独立拆任务。
2. 从现有布局提取默认应用插件，接管 Sidebar、Inspector、全局弹窗框架、命令面板、导航和布局持久化。业务子面板调用原领域插件；不把全部 app-store 搬到一个新插件后要求其他插件导入它。
3. App 根改为按组合挂载应用入口；默认与外部布局走同一前端加载器，复用 B4 共享 React/Zustand 运行时。不保留默认 React 组件分支或布局失效时自动复活的宿主 UI。
4. 按页面和领域拆 store：内核只保留装配/连接/恢复状态，布局只持有选择和呈现状态，会话/审批/AGY 等由原插件拥有。shell bridge 调用逐个改公开服务/导航，尚待 W2/W3 迁出的适配要列明调用方和清除归属。
5. 快捷键、菜单、托盘动作和导航贡献在插件生命周期注册。系统窗口关闭/退出等通用动作可留内核；业务快捷键处理 IME、焦点、重复注册和启停。
6. KernelRecoveryView 使用独立客户端和最小状态，不导入业务 app-store、ModalHost、Sidebar 或聊天模块；入口未绑定、加载失败、自停用和恢复均能进入。
7. 保留文件导航语义：Windows 盘符、file URI、相对路径、空格/中文、行列号进入文件插件侧栏；无法预览时给出明确结果，不整页跳走。保留已有外链打开方式。
8. 更换布局不停止后台轮次；草稿、会话绑定、文件预览和已有插件页可恢复。布局热换失败可还原修订；确需重启的入口返回明确重启状态。

### 6.2 W1 完成交付

- 应用入口、导航、贡献与独立恢复可运行；更换/停用旧布局后其快捷键、事件和菜单不再触发。

1. 按 W1 公共接缝迁移设置、插件中心、实例/绑定/组合管理、来源浏览及相关 ModalHost 页面，归普通管理插件。内核安装/修订/信任/生命周期 API 保留，管理界面不能反向拥有内核。

3. PluginAuthoring、PluginBuilderV2 的工作流、模板、路由、构建诊断、预览和后台任务由开发工具插件启动/停止；删除 app.ts 对它们的直接创建。不能只是插件调用仍常驻宿主的 Builder 单例。

7. 支持关闭管理/开发工具插件、坏自更新、回退上一修订和恢复组合。内核最小恢复入口仍可安装/停用/恢复，不强行重启完整插件中心作为恢复依赖。
8. 用一个外部替代管理界面消费同一公共 API，并用 AI 开发流程制作一个此前不存在的导航/页面/服务贡献插件。实现只改插件及组合；发现缺失通用能力时补公开原语和示例，不新增业务特判。

## 8. B5-W3：远程、内核收尾、性能与最终交付

分支：`codex/b5-w3-kernel`。正式开发前合入完整 W2 固定 SHA，核对包含完整 W1；不从旧基线重复实现前两包。

### 8.1 远程迁移

1. 配对码、设备记录/撤销、远程会话订阅、同步策略、远程界面及旧协议适配归远程插件；内核保留通用认证/路由/连接/撤销原语。
2. 替换 app.ts 对 RemoteAuthService 和远程领域回调的直接依赖，WS 网关不再按原生厂商/业务帧枚举默认模块。旧 URL/帧适配作为普通兼容插件随默认组合分发，可关闭。
3. 保留现有本地管理与设备身份边界；设备撤销后既有连接/订阅按协议终止，不能向远程页面发送本地全权令牌。迁移不靠删除鉴权或默认放开全部远程端点完成。
4. 远程插件停用后配对和设备业务入口/监听任务退出；本地窗口、插件恢复和本地会话不依赖它。通用监听端口可由启动配置保留，但不能继续执行已停用的远程业务。
5. 外部 remote-lite 证明相同机制可提供独立远程业务。离线集成必须走真实设备 principal/注册路由和 WS，避免 loopback 自动本地授权掩盖鉴权；真实手机/LAN/OAuth 有条件才测，未测如实记录。

### 8.2 数据、启动、包入口和兼容清理

1. 按表和方法列出 HarnessMateStore 的所有者，涉及会话、运行/原生绑定、导入水位、Git/终端、审批、设备等。每个领域的 DDL/迁移/查询归所属插件；跨域引用通过公开契约或明确的同库事务协调，不复制双写权威数据。
2. 内核库仅保留包修订、信任、实例/组合、通用 KV/迁移记录等内核数据。通用连接可以留内核，但打开新空库不创建业务表；不允许先构造完整旧 store，再用停用标记掩盖已做的初始化。
3. 旧库保持表名、ID、seq、native ID、导入/搜索水位、绑定和已结算状态；登记既有迁移时检查结构而非重复执行建表。迁移依赖、事务、失败回退、并发首次启动有明确顺序。
4. 保留共享连接/事务的必要原子性。可将旧查询方法迁入领域适配文件，但其实例和调用权必须跟随插件生命周期；不允许把整个单体 store 搬成一个永远必需的业务总插件冒充逐域解耦。
5. 解开 builtin/services 的静态默认领域工厂表与 PluginManager.firstParty 专路，捆绑插件也通过公开包入口/清单加载。保留旧 ID 和来源兼容元数据，但来源不决定特权注册或禁用行为。
6. 清理 app.ts、WS、Electron 和 Web 入口的直接领域初始化、业务 action 和宿主 fallback；B1–B4 旧兼容路由由对应插件/普通兼容插件持有。停用提供者后返回不可用，不能创建默认备用实例。
7. 更新 stage-bundle 和前端构建：业务资源仍可随 EXE 分发，但不能在空组合时导入执行。生成内核可达模块/业务入口清单，用构建依赖图和运行期记录共同证明；纯类型引用单列。
8. 完成领域“功能→所有者→清单入口→API/视图→表/任务→停用/回退”总表。未迁项必须明确列出，不能用大而全的兼容 manager 或总 store 把清单归零。

## 10. 配置、数据与回退实施规则

1. 每包先导出配置/组合和数据副本，记录原实例、绑定、修订及旧配置字段映射；所有临时文件、证据、依赖缓存和打包数据放 D 盘。

3. 区分四种回退：停用实例、回退插件修订、恢复组合/绑定、回到旧 EXE。对需要重启的改变给出明确状态和重启入口，重启后可从内核恢复。
4. B4 回退包为 `D:/HarnessMate/b4-tmp/w3/HarnessMate-Desktop-B4-portable.exe`。复制种子库，用 B5 打开并新增会话/事件、绑定、审批或规则及配置，再由真实 B4 EXE 读回副本；不在用户原数据上做验收。
5. 插件进程外已发生的写文件/网络等副作用不宣称能随组合自动撤销。报告描述资源释放和数据保留的真实边界。
6. 通用能力补丁也须能随插件停用释放其使用资源；若调整宿主原语，提供可恢复提交和兼容策略。不能以“插件自由化”为理由绕过已有实例身份、代次或远程身份校验。
